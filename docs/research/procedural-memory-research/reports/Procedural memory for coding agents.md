# Store pitfalls, point to code, abstain often

The best-supported way to keep procedural memory for coding agents is to store short, abstract, verified items (mostly pitfalls and strategies), pick at most one of them with a precise retriever, show nothing when the match is weak, and check anything that names code against the current tree before the agent sees it. Long templates, raw trajectories and loosely matched memories often do worse than no memory at all: on SWE Context Bench, freely retrieved summaries scored 22.22% against a 26.26% no-memory baseline, while the same summaries chosen by an oracle scored 34.34% ([arXiv 2602.08316](https://arxiv.org/html/2602.08316)). On a coding memory benchmark, 11 of 12 pairings of solver and memory system failed to beat memory off ([VibeMemBench, arXiv 2609.23570](https://arxiv.org/abs/2609.23570)). Singularity's own design sits at the risky end on three choices: substring cues (the weakest kind of retrieval), blanks filled by position (no supporting evidence), and full workflow bodies pushed at task start (the form agents copy most closely). Its own daily-use test matches that prediction: same pass rate or worse, agent cost up 9 to 13%, and all-in cost up 76 to 79% once learning is counted ([critique, section 2](/mnt/project-files/memory-critique/critique.md)). The parts the literature supports are the parts Singularity already found working: trap warnings, commands and their order, and places re-found in today's code. Singularity should rebuild around those, measure against plain git history on held-out commits, and stop guessing values and showing low-confidence matches.

## Short abstract items beat long templates once tasks differ

No single format wins everywhere, but the pattern across studies is steady. Concrete traces help when the new task is a near twin of an old one. Abstract items help as the gap grows. Agent Workflow Memory (AWM) stores natural-language workflows with placeholders such as `{product-name}` and reports **35.5% success on WebArena against 23.5%** for its baseline. Its margin over MindAct on Mind2Web grows from about 7.4 to 16.9 step-success points as splits move from cross-task to cross-domain ([AWM, arXiv 2409.07429](https://arxiv.org/html/2409.07429v1)). Mem^p found raw trajectories did better on the dev split and distilled scripts did better on the test split, with the two combined doing best ([arXiv 2508.06433](https://arxiv.org/html/2508.06433v3)). ExpeL found the same split by task type: insights beat retrieved trajectories on HotpotQA (36% against 31%) and lost on ALFWorld (50% against 55%), where exact action sets matter ([arXiv 2308.10144](https://arxiv.org/html/2308.10144v3)). A 2026 study measured cross-task reuse directly: **raw trajectories gave -9.5 points** on ALFWorld A to B, while abstracted insights gave +6.5 ([arXiv 2604.27003](https://arxiv.org/html/2604.27003v1)).

Coding results point the same way, and they are smaller. SWE-Exp, which keeps experiences free of object names and shares them across repositories, lost 6 points (42.0% to 36.0%, DeepSeek-V3, SWE-bench Verified) when it used the raw issue and gold patch in place of its abstracted experience ([arXiv 2507.23361](https://arxiv.org/html/2507.23361v2)). On SWE Context Bench, the oracle-chosen summary averaged **about 217 tokens and added 8 points**, while the oracle-chosen full trajectory averaged about 25,600 tokens and added 1 point ([arXiv 2602.08316](https://arxiv.org/html/2602.08316)). That benchmark's Lite split has only 99 evaluation tasks and reports no confidence intervals, so gaps of a few points sit within noise ([papers notes, citing arXiv 2602.08316](https://arxiv.org/html/2602.08316)). Agent KB found structured experiences beat raw workflows on GAIA (61.21 against 58.18), but its prose claims larger gains than its tables show ([arXiv 2507.06229](https://arxiv.org/pdf/2507.06229v5)).

Executable skills are a separate case. ASI verifies induced programs by running them and credits most of its WebArena gain to that check; SkillWeaver and Voyager report large gains from executable skill libraries ([ASI, arXiv 2504.06821](https://arxiv.org/abs/2504.06821); [SkillWeaver, arXiv 2504.07079](https://arxiv.org/abs/2504.07079); [Voyager, arXiv 2305.16291](https://arxiv.org/abs/2305.16291)). Those numbers were read from abstracts only, so sample sizes and ablations were not checked. A later budget-matched study also found that ASI's verified skills failed on their first step in up to 72% of Shopping verifications under GPT, because they pointed at unstable element IDs ([arXiv 2606.15017](https://arxiv.org/pdf/2606.15017)). That is the web version of a workflow step that names code which has since moved.

The closest published analogue to Singularity is Agentic Plan Caching (APC). It stores keyword and plan-template pairs with names and numbers removed, saves a template only after a run "finished with correct outputs", and on a hit asks a small model (LLaMA-3.1-8B) to adapt the template ([APC, arXiv 2506.14852](https://arxiv.org/html/2506.14852v2)). It reports a 50.31% average cost cut while keeping 96.61% of best accuracy. The details matter for Singularity. APC's key is one higher-level **intent keyword extracted by a model**, because keys built from the query's surface words "overweight names" and gave more false hits and misses. Looser fuzzy matching raised the hit rate (46% to 64%) but cut accuracy (85.5% to 77.0%). Hit rates were low on heterogeneous tasks, and the authors suggest turning caching off when hits stay low ([arXiv 2506.14852](https://arxiv.org/html/2506.14852v2)). Singularity keeps APC's template idea but drops all three of its safeguards: surface substrings in place of intent keys, positional filling in place of a model, and no hit-rate check. Singularity's own finding that from two bug fixes the model "kept what each did, not what both did", and that memory did not help on validator.js, fits a template store that generalizes poorly ([critique, section 9](/mnt/project-files/memory-critique/critique.md)).

## Picking the right item matters more than the item, and substring cues pick worst

Retrieval failure, more than bad content, is what sinks memory. On LoCoMo, retrieval precision tracked accuracy at **r = 0.98**, and retrieval failure caused 11 to 46% of errors against 4 to 8% for failing to use a correct memory. BM25 averaged 57.1%, dense cosine 73.4%, and hybrid with a reranker 77.2% ([arXiv 2603.02473](https://arxiv.org/html/2603.02473v2)). A procedural retrieval benchmark on ALFWorld found BM25 lost **42.5% of its quality** (MAP 0.815 to 0.469) when object words changed, and keyword Jaccard lost 41.5%. Embedding an object-free LLM summary of each procedure lost only 11% and went from last place on seen queries to first on unseen ones ([arXiv 2511.21730](https://arxiv.org/html/2511.21730v1)). Exact substring matching, which Singularity uses (`Cues.ts:36-45`), is more brittle than either BM25 or Jaccard. No study measured it directly, so this ranking is an inference from those two numbers ([retrieval notes, citing arXiv 2511.21730](https://arxiv.org/html/2511.21730v1)).

Singularity's evals show both failure modes the literature predicts. Look-alike prompts got the wrong memory ("built-in rules" pulled every new-rule workflow, "main menu" pulled a Preferences toggle), and paraphrases got nothing, so the save-as bug runs were in effect no-memory runs ([critique, section 4](/mnt/project-files/memory-critique/critique.md)). Code retrieval is a partial exception: BM25 stays strong for code-to-code search and beat a dense code retriever on SWE-bench-Lite file retrieval (NDCG 43.0 against 29.1) ([CodeRAG-Bench, arXiv 2406.14497](https://arxiv.org/html/2406.14497v2)). That supports lexical matching for finding *places* in code, which Singularity does by surrounding blocks, and does not support it for deciding *which procedure applies* to a prompt.

How many items to show is also settled for coding. SWE-Exp peaked at exactly one experience: **0 gave 37.8%, 1 gave 42.0%, 2 gave 39.8% and 4 gave 39.0%**, and dropping its LLM rerank that picks 1 of the top 10 cost 3.8 points ([arXiv 2507.23361](https://arxiv.org/html/2507.23361v2)). The paper also reports the no-experience figure as 37.2% elsewhere in its text ([papers notes, citing arXiv 2507.23361](https://arxiv.org/html/2507.23361v2)). Xiong et al. found that adding every memory fell 16 to 22% (relative) below a fixed memory, while a strict quality filter gained, for example EHRAgent 13.05 to 38.50 ([arXiv 2505.16067](https://arxiv.org/html/2505.16067v2)). Adaptive and gated retrieval in RAG (CRAG, Self-RAG, Mallen et al.) beats always retrieving, but those results were noted at abstract level only ([CRAG, arXiv 2401.15884](https://arxiv.org/abs/2401.15884); [Mallen et al., arXiv 2212.10511](https://arxiv.org/abs/2212.10511)). No paper found reports a tuned threshold for procedural memory, so Singularity would have to calibrate its own.

Abstaining matters more in a single repository than one might expect. In SWE-Bench-CL, tasks from the same repository were only weakly alike (patch TF-IDF cosine 0.179; one pair of tasks above 0.4) ([arXiv 2507.00014](https://arxiv.org/html/2507.00014v1)). Evo-Memory found gains tracked within-dataset task similarity (Pearson r = 0.717 on Gemini, 0.563 on Claude) ([arXiv 2511.20857](https://arxiv.org/html/2511.20857v1)). Most new tasks will not have a close stored twin, so a memory that injects something on most tasks will inject the wrong thing on many of them.

Push beats pull for knowledge the agent does not know it lacks. In Vercel's Next.js evals the agent never invoked an available skill in 56% of cases; a skill alone gave no gain over a 53% baseline, a skill plus an explicit instruction gave 79%, and a compressed docs index always present in AGENTS.md gave 100% ([Vercel](https://vercel.com/blog/agents-md-outperforms-skills-in-our-agent-evals)). Singularity saw the same thing: no agent in either arm ran `recall` or the skill ([critique, section 12](/mnt/project-files/memory-critique/critique.md)). Push has a cost, though. Agents follow retrieved memory almost mechanically, with input and output similarity correlated near r = 1 for one agent ([arXiv 2505.16067](https://arxiv.org/html/2505.16067v2)), and related-but-wrong text hurts more than unrelated text ([Chroma context rot summary](https://www.zenml.io/llmops-database/context-rot-evaluating-llm-performance-degradation-with-increasing-input-tokens)). Length alone also hurts: one study found accuracy fell with added masked tokens even when retrieval was perfect ([arXiv 2510.05381](https://arxiv.org/html/2510.05381v1)). The design these results support is a hybrid: push a small, high-precision index or pointer, and let the agent open the detail. Singularity's current hand-over of 10,000 to 18,000 characters, reread every turn even when the pick is wrong, is the opposite ([critique, section 4](/mnt/project-files/memory-critique/critique.md)).

## Wrong values and stale text get copied, so verify or say nothing

Filling a blank by position ("the Nth code span") has no supporting study. The dominant practice is to abstract values away at storage time and let a model fill or adapt at use time, as AWM, SWE-Exp's reuser agent and APC's small model all do ([AWM, arXiv 2409.07429](https://arxiv.org/abs/2409.07429); [arXiv 2507.23361](https://arxiv.org/html/2507.23361v2); [arXiv 2506.14852](https://arxiv.org/html/2506.14852v2)). No controlled comparison of rule-based and model-based slot filling was found. Because agents copy retrieved records closely ([arXiv 2505.16067](https://arxiv.org/html/2505.16067v2)), a wrong value stated in the first prompt is likely to be used. Singularity filled `{tag}` with "# Install" and with `npm test`, and before the late `partsChoice` fix it told a stats change to use another change's key ([critique, section 5](/mnt/project-files/memory-critique/critique.md)).

Stale text has the same effect. In a preliminary benchmark, all 10 models scored 0 of 6 and read no files when a CLAUDE.md-style summary held six stale facts, even though current notes were on disk. A summary that *pointed to* the notes let agents find the right values. Corrections labelled "provisional" did nothing, and pushing correct facts scored 6 of 6 on every model. That study ran only 2 to 3 trials per cell with no significance tests ([Meetless stale-context benchmark](https://research.meetless.ai/stale-context/)). TEPA, a 2026 preprint with some table inconsistencies, found that superseded memories left active made append-only memory **worse than no memory** under drift (0.203 against 0.298 in an executable, file-backed setting, 50 seeds), while revoking them reached 0.950 ([arXiv 2608.07429](https://arxiv.org/pdf/2608.07429)). MemStrata, a draft that is not peer reviewed, found cosine similarity could not tell contradictions from duplicates (AUROC 0.59 on 98 pairs) and that a deterministic supersession ledger fixed renames and config moves in code scenarios ([arXiv 2606.26511](https://huggingface.co/papers/2606.26511.md)). Singularity's stale cases are exactly these: a step told the agent to create files in `doc-build/` after the folder became `doc-src/`, and a learned UI step submitted the wrong form after an update ([critique, section 6](/mnt/project-files/memory-critique/critique.md)).

The one shipped design with controlled evidence is GitHub Copilot Memory. Each memory is a fact plus `file:line` citations and a reason. Before use, the agent checks the cited code; if the code disagrees it stores a corrected version, and if it agrees it re-stores the memory to refresh its timestamp. Unused memories are deleted after 28 days. In an A/B test the coding agent's **PR merge rate rose from 83% to 90%** (p < 0.00001), and seeded false memories were caught "in all cases" ([GitHub Blog](https://github.blog/ai-and-ml/github-copilot/building-an-agentic-memory-system-for-github-copilot/); [GitHub Docs](https://docs.github.com/en/copilot/concepts/agents/copilot-memory)). That is a vendor A/B with no released data, and it was not designed to isolate the verification step ([papers notes, citing the GitHub blog](https://github.blog/2026-01-09-building-an-agentic-memory-system-for-github-copilot)). Singularity already re-finds places in today's code, which is the right half. It does not check the step text, and it shows steps whose places it cannot verify. In a code repository the natural invalidation key is deterministic: a commit that touches an item's anchored blocks or renames its paths ([freshness notes, citing TEPA](https://arxiv.org/pdf/2608.07429)).

How memory is rewritten also matters. ACE reports that repeated whole-context rewrites cause "context collapse" and favor short generic text ("brevity bias"), and that itemized delta updates merged by plain code, with helpful and harmful counters per bullet, avoid both ([ACE, arXiv 2510.04618](https://arxiv.org/pdf/2510.04618)). Its widely quoted example is a Dynamic Cheatsheet context that went from 18,282 tokens at 66.7% accuracy to 122 tokens at 57.1%, below the 63.7% no-context baseline, in one rewrite. The notes disagree on whether that number was checked: one set reports it from the ACE full text, while another says it was not visible in the abstract fetched and should be verified before quoting ([arXiv 2510.04618](https://arxiv.org/abs/2510.04618v2)). Treat the exact figures as unconfirmed; the qualitative warning is consistent across both notes. Singularity rewrites workflows after every 3 commits ([critique, How it works](/mnt/project-files/memory-critique/critique.md)), which is the pattern ACE warns against.

## Pitfall warnings earn their place, and git history is the free rival

Across studies, failure-derived memory helps when it is distilled into conditional pitfall statements and hurts when failed runs become procedures. ReasoningBank's ablation on WebArena-Shopping is the cleanest case: adding failure lessons raised its own score from 46.5 to 49.7, while the same failures **lowered AWM's workflow memory from 44.4 to 42.2** ([ReasoningBank, arXiv 2509.25140](https://arxiv.org/html/2509.25140v1)). ReasoningBank also reported SWE-bench Verified gains of 34.2 to 38.8 (Gemini-2.5-flash) and 54.0 to 57.4 (Gemini-2.5-pro) with fewer steps ([arXiv 2509.25140](https://arxiv.org/html/2509.25140v1)). Letta's skills, which encode "approaches, common pitfalls, and verification strategies", gained 9 points on Terminal-Bench 2.0 from trajectories alone and 15.7 with verifier feedback, but the skills were learned on the same 89 tasks used for testing, with one model and no variance reported ([Letta](https://www.letta.com/blog/skill-learning)). AutoGuide retrieves conditional guidelines ("in context C, do or avoid X") only when their context matches and reports beating ExpeL, though its numbers were not retrieved ([AutoGuide, arXiv 2403.08978](https://arxiv.org/html/2403.08978v2)). No study isolates warnings-only against procedures-only on coding tasks with matched token budgets, so the case for warnings rests on consistent direction across studies, not on a direct test ([freshness notes](https://arxiv.org/html/2509.25140v1)).

Studies of context files agree on content. In "Evaluating AGENTS.md" (138 AGENTbench tasks plus 300 SWE-bench Lite tasks, one run per instance), LLM-generated context files lowered resolution in 5 of 8 settings and raised cost by about 20 to 23%, codebase overviews did not shorten the path to relevant files, and specific tooling instructions were followed (uv used 1.6 times per instance when mentioned, under 0.01 when not) ([arXiv 2602.11988](https://arxiv.org/html/2602.11988v1)). A secondary summary puts developer-written files at about +4% and generated files at about -3% ([Daniel Vaughan summary](https://codex.danielvaughan.com/2026/07/27/do-auto-generated-agents-md-files-actually-help-codex-cli/)), which differs from the primary note's -0.5% to -2% for generated files. Claude Code's auto memory deliberately skips "anything it can derive from the codebase, such as architecture, file paths, or debugging fixes" ([Claude Code docs](https://code.claude.com/docs/en/memory.md)). These match Singularity's results: its clearest wins were traps such as the `handleKeyboardGlobally` test trap and the `--watch=false` error, and command order ([critique, What I would do](/mnt/project-files/memory-critique/critique.md)). Command order also caused its one memory-induced failure, when a learned closing command put `build-docs` before `build-config` ([critique, section 2](/mnt/project-files/memory-critique/critique.md)), so commands need the same verification as steps.

Git history is a strong, free baseline. HAFixAgent injected context from `git blame` on buggy lines and fixed **545 against 522 bugs on Defects4J (+4.4%) and 377 against 272 on BugsInPy (+38.6%)**, with a union of three history heuristics at +31% and +70.2%, and no significant change in steps or cost in most categories. It assumes perfect fault localization and counts plausible patches ([arXiv 2511.01047](https://arxiv.org/html/2511.01047)). VibeMemBench found that verified experience injected directly raised resolution by 1.1 to 4.5 points on 4 of 5 held-out solvers, while packaged memory systems mostly failed to deliver it. Its targets were kept only where injected history helped in a reference setting, so its upside is likely optimistic, and its solver list was not visible in the abstract ([arXiv 2609.23570](https://arxiv.org/abs/2609.23570)). Singularity's markdownlint test shows the same thing from the inside: agents without memory looked up earlier commits before their first edit in 7 to 8 of 12 sessions and cut their cost from $0.49 to $0.24 by task 4, and agents with memory looked up the commit anyway in 6 of 12 sessions, paying twice ([critique, section 1](/mnt/project-files/memory-critique/critique.md)). A short hand-written guide also beat memory v2 on the web benchmark, 23 of 23 against 21 ([critique, section 10](/mnt/project-files/memory-critique/critique.md)). What git does not hold is where to look, which mistakes cost turns, and which checks to run. Those are the parts memory can add ([freshness notes, citing HAFixAgent](https://arxiv.org/html/2511.01047)).

## Singularity's evals cannot yet tell a win from noise

The evaluation literature sets four bars, and Singularity's gate misses all of them. First, test on held-out tasks, ideally later in time. SWE-Bench-CL orders tasks chronologically for this reason ([arXiv 2507.00014](https://arxiv.org/html/2507.00014v1)). Singularity keeps a new memory version if a replay over the same changes it just learned from does not score lower, using a places-shown proxy (`Evolve.ts:161-167`) ([critique, section 8](/mnt/project-files/memory-critique/critique.md)). Experience-following makes in-sample replay flatter memory, because copying looks good when the task resembles its source ([arXiv 2505.16067](https://arxiv.org/html/2505.16067v2)).

Second, run enough repeats. On SWE-bench Verified, single-run pass@1 varies by 2.2 to 6.0 points between identical runs; detecting a 2-point gain at 80% power needs about 9 runs per agent, and a 10-point gain about 1 ([arXiv 2602.07150](https://arxiv.org/html/2602.07150v2)). Singularity's daily-use test ran once per task per arm, and its other tests ran 3 to 4 times per side, where validator.js found "the spread within each setup is wider than the difference between them" ([critique, section 11](/mnt/project-files/memory-critique/critique.md)). Many fixes were also found on the same tasks they were tested on ([critique, section 11](/mnt/project-files/memory-critique/critique.md)). The headline result (28.5 turns to 9.5) used hand-built memory frozen on the repo it was tuned against, with near-twin tasks and a fix added for that exact task just before the runs ([critique, section 3](/mnt/project-files/memory-critique/critique.md)). That makes it in-sample in every sense the literature warns about.

Third, charge memory for what it costs, and compare against a plain agent given the same extra budget. A plain WebArena agent given 15 steps in place of 10 matched or beat AWM, ASI and ReasoningBank with all three models tested, for example 50.7% at 71.9K tokens against ASI's 47.9% at 107.1K ([arXiv 2606.15017](https://arxiv.org/pdf/2606.15017)). Singularity's learning cost $2.59 to $2.63 in markdownlint, two thirds of the whole no-memory agent bill of $3.93, and half the rounds were rejected by the gate ([critique, section 7](/mnt/project-files/memory-critique/critique.md)). No published guidance on break-even for memory-building cost was found, so that analysis has to be done in-house ([freshness notes](https://arxiv.org/pdf/2606.15017)).

Fourth, include simple baselines. Evo-Memory found that plain top-k retrieval of similar past experiences (ExpRAG) was "highly effective" and tied the proposed method on Claude single-turn (0.59 against 0.58) ([arXiv 2511.20857](https://arxiv.org/html/2511.20857v1)). For Singularity, the simple baselines are no memory, a `git log --stat` or `git log -p` of recent related commits, the most similar past commit diff, and a short hand-written guide ([critique, What I would do](/mnt/project-files/memory-critique/critique.md)).

## Conclusion

The evidence shifts the question Singularity should ask. The useful question is "when is the agent better off with this one verified item than with nothing and `git log`?", and the literature says the honest answer is "rarely, but reliably for pitfalls and checks, when the pick is confident." Singularity's own data already says the same thing, which makes the redesign lower risk than it looks: the parts it would keep are the parts that worked in its tests, and the parts it would cut are the parts that caused its failures.

Two gaps limit every conclusion here. No study compares templated workflows against pitfall-only memory on coding tasks at matched budgets, and none compares learned memory against git history on the same tasks at matched cost ([papers notes](https://arxiv.org/html/2602.08316); [freshness notes](https://arxiv.org/html/2511.01047)). Singularity is unusually well placed to run both, because it already records commits, places and outcomes in real repositories. A held-out, repeated, budget-matched result from Singularity would be new evidence for the field, whichever way it comes out.
